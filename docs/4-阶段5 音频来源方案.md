# 阶段 5：驱动从哪里取声音——方案选型

现状：已有驱动 `LdacA2dp`（AVDTP + L2CAP，通过 IOCTL 接收现成的媒体包）和服务 `ldacsvc`（采集 → 重采样 → LDAC/SBC → 打包）。还缺一个应用程序可向其输出声音的 Windows 音频端点。需要在开始阶段 5 之前作出决定。

## Alternative A2DP 的做法

`AltA2DP.sys` 是安装在 A2DP 设备 `BTHENUM\{0000110b-…}` 上的单一音频驱动（类 `MEDIA`，`ks.inf`/`wdmaudio.inf`，Wave 和 Topology 过滤器）。端点「耳机（JBL Live 780NC）」属于蓝牙设备本身，编码在内核中完成，没有单独的服务。详见 `docs/jbl-live-780nc.md`。

## 方案 A——全部放在内核，与 Alternative A2DP 相同

驱动变为 `BTHENUM` 设备上的音频驱动（PortCls WaveRT 或 ACX），自行编码 LDAC/SBC 并发送数据包。

- **优点：** 端点就是耳机本身，带耳机的名称和图标。延迟最低。无需常驻运行的服务。音量和 AVRCP 更易关联。
- **缺点：** libldac 和 ABR 要在内核中运行。那就需要定点（fixed-point）构建（`_32BIT_FIXED_POINT`），而且编解码器的任何错误都会导致蓝屏。内核中代码量最大、调试最困难。经过验证的服务 `ldacsvc` 无法进入最终构建。

## 方案 B——虚拟音频设备 + 服务

单独的虚拟音频驱动（ACX，参照 WDK 示例）创建端点「JBL Live 780NC (LDAC)」。`ldacsvc` 从其中取出 PCM，并按现状把数据包传给 `LdacA2dp`。

- **优点：** 编解码器留在用户态：它出错最多只会让服务崩溃。几乎整条链路都已编写并验证。端点更简单：就是普通的虚拟音频驱动。
- **缺点：** 系统中会多出一个设备。需要在耳机连接和断开时创建与移除它，还要切换默认设备。另外在内核 → 服务 → 内核的往返上会增加 20–40 ms 延迟。两个驱动而不是一个，两者都要签名。

## 方案 C——混合式：端点在蓝牙设备本身，编解码器在服务中

`LdacA2dp`（它已是 KMDF 驱动）在同一个 `BTHENUM` 设备上额外挂起 ACX 渲染方案，与 Alternative A2DP 一样。驱动通过 IOCTL 或共享内存，把 WaveRT 环形缓冲区中的声音交给服务。服务完成编码后，通过已有的 `IOCTL_LDACA2DP_SEND_MEDIA` 把数据包送回。

- **优点：** 从外部看一切都与 Alternative A2DP 相同：一个设备、正确的名称、类 `MEDIA`。而编解码器在用户态，`ldacsvc` 几乎无需改动即可使用（只改变声音来源）。没有第二个驱动，也没有虚拟设备的生命周期。
- **缺点：** 在 `BTHENUM` 设备上使用 ACX 属于非标准组合，需要花功夫弄清楚。还需要一条内核 → 服务的 PCM 通道，并监控缓冲区欠载。延迟与方案 B 相当。服务未运行时端点会沉默：这一状态需要处理（静默或隐藏）。

## 建议

**方案 C。** 它能给用户与 Alternative A2DP 相同的体验，却不把编解码器搬进内核，也不丢弃经过验证的服务。如果 `BTHENUM` 上的 ACX 被证明无法攻克，同一条内核 → 服务的 PCM 通道几乎无需大改即可移植到单独的虚拟设备（方案 B）。只有在方案 C 的延迟被证实明显时才考虑方案 A。

## 实际实现（方案 C，2026-10-22）

- **驱动**（`driver/LdacA2dp/audio.c`）在 `AddDevice` 时初始化 ACX（1.1，KMDF 1.31），并创建播放方案 `Headphones0`。主机引脚（host pin）接受 44.1/48 kHz 16 bit，以及 48/88.2/96 kHz 的 24 位封装于 32 位；桥接引脚（bridge pin）为 `KSNODETYPE_HEADPHONES`。没有音量元素：Windows 音量以软件方式应用，AVRCP 另行添加。INF 把设备归入 `MEDIA` 类，并注册接口 `KSCATEGORY_AUDIO/RENDER/REALTIME`，引用 `Headphones0`。
- **WaveRT 流**由定时器驱动，方式与 WDK 示例 `audio/Acx/Samples/AudioCodec` 相同：每个包按其时长「播放」，随后驱动报告完成（`AcxRtStreamNotifyPacketComplete`）并把该包复制到 256 KB 的环形缓冲区（96 kHz / 32 bit 下约 330 ms）。
- **通往服务的通道** —— `IOCTL_LDACA2DP_READ_PCM`。响应为：头 `LDACA2DP_PCM_HEADER`（格式与断流标志）加 PCM。若没有数据，请求会在手动队列中等待。若无人读取，旧数据会被覆盖，下一个响应将带上 `DISCONTINUITY` 标志。
- **我们的 IOCTL 接口与 ACX 在同一设备上共存**：ACX 只处理其自身方案的描述符，而对 `GUID_DEVINTERFACE_LDACA2DP` 的请求仍进入我们的默认队列。这已在测试台上验证。
- **服务**：来源为 `endpoint`（`--sink driver` 时的默认值）。采样率跟随端点流的格式，重采样器即时重建。一旦有数据就发送 START，与音量无关；数据停止 3 秒后发送 SUSPEND。

测试台上 Windows 中出现了端点「耳机（LDAC A2DP Source）」。用普通播放器播放到该端点的声音，会以 LDAC SQ、125 包/秒传送到耳机，无丢包。

**声音刚开始时。** START 之后，JBL Live 780NC 在大约 0.5 秒内几乎不接收媒体包：450 ms 内的前 33 个包只发出去 5 个，随后队列一下清空。若此时正在播放声音，耳机会出现卡顿，而 ABR 会在约 10 秒内把质量降到 MQ。因此在 START 之后，服务会按实时速率发送静音，直到链路通畅：最近 100 ms 内至少应有 70% 的包发出，整个预热过程持续 300 ms 到 2 秒。为避免增加延迟，服务不会把多余的静音排到超过 3 个包的深度。之后编码器回到所选质量，声音在 30 ms 内平滑升高。START 本身耗时 0.6–1.3 秒。在 START 和预热期间声音会丢失：最初约 1.2 秒。听感上这是一次「顿卡」——从中间断掉的音符。PCM 记录（`--pcm-dump`）表明 Windows → 驱动 → 服务这条路径不会引入断流。若声音之前本来就有一段静音，起播就是干净的（经听感验证）。

**只要 Windows 流处于打开状态，流就保持。** 驱动在状态中报告 `PcmOpen`：音频引擎打开了端点流，无论它在播放还是暂停。只要它打开着，服务就不发送 SUSPEND；若没有声音，服务会自己按严格的实时速率送入静音。否则链路会「入睡」，恢复时又要停顿 0.5 秒。这是在测试台上发现的两个陷阱。第一：Windows 中 5 ms 的等待实际耗时约 15.6 ms（一个定时器步长），因此固定大小的数据块会落后三分之一，耳机缓冲在暂停期间被抽空，恢复时出现卡顿。第二：最初 50 ms 的静音（服务察觉暂停所需的时间）不予补发，因为这样的突发包会被 ABR 视为过载。在测试台上使用 WPF 播放器（`MediaPlayer`）：播放、暂停、播放——一次 START、一次预热，暂停期间 125 包/秒，全程 SQ，恢复时听感干净。程序关闭流时 Windows 才会关闭流。`SoundPlayer` 和通知音在播放后立即关闭流，因此对它们来说，3 秒静音后仍会发送 SUSPEND，下一次声音又要重新经历 START 和预热。

**名称。** Windows 把端点命名为「<类型>（<设备 FriendlyName>）」。驱动在 `PrepareHardware` 中通过 `IOCTL_INTERNAL_BTHENUM_GET_DEVINFO` 取得耳机名称，并写入 `DEVPKEY_Device_FriendlyName`。这一过程发生在方案被添加之前，因此端点从一开始就叫「耳机（JBL Live 780NC）」。

**AVRCP 与音量。**

- **驱动。** 同一个 `LdacA2dp.sys` 会安装在耳机的三个设备上，角色由服务 UUID 判定：
  - `110B` — A2DP；
  - `110E` — AVRCP；
  - `110C` — 空角色，仅用于让系统自带的 `AvrcpTransport` 远离 PSM 0x17。
- **内核。** AVRCP/AVCTP 位于 `avdtp/src/avrcp.c`，不使用堆，并有基于参考记录的测试。
- **绝对音量。** 端点方案中包含音量与静音元素（−63.5…0 dB），因此 Windows 不再缩放 PCM。滑块以 `SetAbsoluteVolume` 的形式发到耳机，而来自耳机的 `VOLUME_CHANGED` 会移动滑块。刻度对滑块位置呈线性（X % → 127·X %）。Windows 的曲线（约 34 dB/十倍频程）我在测试台上实测后以表格形式放入了 `audio.c`。
- **没有绝对音量时**（或 AVRCP 尚未建立时），服务会自行把 PCM 乘以滑块电平，并带平滑过渡。
- **按键**通过虚拟 HID 设备 Consumer Control（VHF，把 `vhf.sys` 作为 `110E` 的下层过滤器）以媒体键形式传入 Windows。
- **AVCTP 何时打开。** 与参考一致：在 A2DP 媒体通道打开之后，最多重试 3 次。若耳机自行打开 AVCTP，则接受该连接。
- **已在测试台验证：**
  - 在耳机中能听到 Windows 音量的变化，编码器之前的信号不会被衰减；
  - JBL 上的音量按键会移动滑块；
  - play/pause 以 `VK_MEDIA_PLAY_PAUSE` 的形式传入 Windows。

尚未完成：端点定时器与耳机之间的延迟和时钟漂移尚未测量。

## 无论选哪种方案，都应先做的事

1. 搭好测试台（`docs/test-stand.md`）并验证已完成的部分：协商，以及通过 `ldacsvc --sink driver` 从 WAV 送出的媒体流。
2. 之后才添加端点。否则音频栈的错误会与协议错误混在一起——与阶段 0 相同的原则。
